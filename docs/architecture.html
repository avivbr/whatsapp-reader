Reading WhatsApp without touching WhatsApp

A TypeScript MCP server that answers questions about 165,000 messages by reading a SQLite file that is already on the disk — and never opens a socket to do it.

Why this shape

The constraint that decides everything

The obvious way to connect an assistant to WhatsApp is a whatsmeow or Baileys bridge that pairs as a linked device. It works, and it is also how accounts get warned and banned — whatsmeow#810 collects reports of the "account may be using unauthorized tools" banner appearing for users doing zero bulk sending, with some accounts banned outright at low volume. The issue is closed as not planned, because the detection is server-side and no library can patch it.

WhatsApp for Mac is Meta's own first-party client. It is already linked, already syncing, and already maintains a complete local store. Reading that file involves no client, no pairing, and no network — so the ban question does not apply at all.

Everything below follows from that one decision. It is also why there is no send_message tool and never will be: sending is the half that would reintroduce the risk this design exists to avoid.

Mechanism

Why we copy the database instead of reading it

This looks like a convenience and is actually a correctness requirement. WhatsApp's store runs in WAL mode. A read-only SQLite connection to a WAL database still needs to create the -shm shared-memory index; against WhatsApp's container that fails with SQLITE_READONLY_CANTINIT unless you pass immutable=1, which risks torn reads while WhatsApp is actively writing.

So: copy, checkpoint, then open the copy read-only. WhatsApp keeps writing throughout and never sees a lock.

Structure

Two adapters, one set of queries

The layering exists to make one class of bug impossible. Query functions are pure, take a database handle, and know nothing about MCP. The CLI and the MCP server are both thin adapters over exactly those functions — so wa search and the search_messages tool cannot drift apart, because there is only one implementation to drift.

The hard part

Sender names, and the two columns that lie

No single column holds a sender's display name, and the two that look like they do are both traps. This chain took real debugging to get right, so it ports across verbatim — comments included.

Timezone is a correctness bug, not a nicety

Timestamps are Core Data seconds from 2001-01-01. Rendering them as UTC silently drops evening messages when you ask "who did I message today" from UTC+3 — this bit us in practice. All date handling goes through one helper in schema.ts, with a test that pins the boundary.

Security posture, carried across unchanged

  • Every read tool annotated readOnlyHint; refresh_snapshot marked non-destructive and idempotent.
  • Server instructions tell the model that message text is third-party data and never instructions — messages are attacker-controllable even without a send tool.
  • No send capability at any point.
  • data/ gitignored; the snapshot is a full plaintext message history and the repo stays private.

Execution

Work order

  1. Spike the SDK first. Install @modelcontextprotocol/server@2.0.0, boot a one-tool stdio server, confirm Claude Code connects. Decide v2 versus v1 before any query logic exists, so the fallback stays cheap.
  2. Scaffold package.json and tsconfig.json with erasableSyntaxOnly.
  3. Port schema.ts and db.ts, then assert snapshot parity against Python — identical row counts across all three databases.
  4. Port the fixture, then the queries module by module with tests. The fixture reproduces both schema traps on purpose; keep that.
  5. Add the three new query modules — people, summary, media.
  6. Wire tools.ts, server.ts, cli.ts.
  7. Repoint .mcp.json and verify in a fresh session.
  8. Delete the Python — src/whatsapp_reader/, pyproject.toml, tests/*.py — and rewrite the README.
