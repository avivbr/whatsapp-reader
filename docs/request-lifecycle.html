Runtime architecture · whatsapp-reader

What happens between your prompt and the database

A prompt you type in Claude Code becomes a JSON-RPC frame down a pipe, a prepared SQLite statement, a few pages of disk, and a JSON reply back up the same pipe. No HTTP, no endpoints, no network — traced and measured end to end.

First, a correction

There are no API endpoints

It is natural to picture a tool call as an HTTP request to an endpoint. That is not what happens here, and the difference is load-bearing for everything below.

whatsapp-reader is a server — but a stdio server, not an HTTP one. When Claude Code starts, it spawns the server as a child process and holds it open for the whole session. The two talk by writing JSON-RPC 2.0 messages to each other's pipes, one JSON object per line. There is no URL, no port, no socket, nothing listening on the network. If you unplugged the machine from every network it would work identically.

So "a tool Claude picks up and uses" is the right mental model. "An endpoint Claude calls" is the wrong mechanical one — there is a process boundary and a pipe, not a request and a route.

# what Claude Code actually runs (from .mcp.json) node --no-warnings /Users/.../whatsapp-reader/src/server.ts # the two frames that open every session, on stdin: {"jsonrpc":"2.0","id":1,"method":"initialize","params":{...}} {"jsonrpc":"2.0","method":"notifications/initialized"} # a tool call, on stdin: {"jsonrpc":"2.0","id":7,"method":"tools/call", "params":{"name":"read_chat","arguments":{"chat":"Family","limit":50}}} # the reply, on stdout — one line, newline-terminated: {"jsonrpc":"2.0","id":7,"result":{"content":[{"type":"text","text":"{...}"}]}}

The lifecycle

Your prompt, from keystroke to answer

Ten hops. You cross the process boundary twice — once down into the server, once back — and the model is invoked twice: first to decide to call the tool, then again to turn the result into an answer.

The data path

How a tool call becomes rows

Inside step 7, the layering is deliberately flat. A tool handler is a thin adapter; the query function it calls is a pure function of a database handle. The same function backs the wa CLI, so the two cannot disagree.

// tools.ts — the adapter, ~10 lines server.registerTool("day_summary", { inputSchema: z.object({ date: DATE.optional() }) }, async ({ date }) => json(withDb((db) => daySummary(db, date)))); // withDb: open read-only, always close — no handle survives the call function withDb(fn) { const db = openSnapshot(); // new DatabaseSync(..., { readOnly: true }) try { return fn(db); } finally { db.close(); } } // queries/summary.ts — the logic, pure over the handle db.prepare(`SELECT ... FROM ZWAMESSAGE m WHERE date(m.ZMESSAGEDATE + 978307200,'unixepoch','localtime') = ?`).all(day);
Every call is independent

A fresh handle per call, closed in a finally. Nothing is cached or held between calls, so two calls cannot interfere and a crash in one leaks nothing into the next. The only durable state in the whole system is the snapshot file on disk.

Performance

Where the milliseconds go

Warm medians of five runs against the real store — 166,655 messages, 1,266 chats — with the OS page cache primed. Cold numbers are two to ten times higher and dominated entirely by first-touch disk reads, not by the code.

OperationWarm median
resolve_phone0.1 ms
resolve_chat0.3 ms
search — common term1.0 ms
list_chats (30)15.8 ms
read_chat (50)20.9 ms
stats121.9 ms
search — rare / absent term231.4 ms

The search asymmetry is the interesting one

A common word (תודה, "thank you") returns in 1 ms; a rare or absent one takes 231 ms. Same query, 200× apart. Search is a LIKE scan with no full-text index, so a common term fills its LIMIT 50 after reading a handful of rows and stops, while a rare term forces SQLite to walk all 166k message bodies before it can be sure there are no more matches. The absent-term case is the true cost of the scan; the common-term case just gets to quit early.

stats is a strftime over every row

Its 122 ms is almost entirely the by-year breakdown, which runs strftime('%Y', …, 'localtime') against all 166k timestamps. Acceptable for a summary you request occasionally; it would be the first thing to precompute if it were called on every turn.

Measurement honesty

These were taken at load average ~4. Earlier in the session the same stats call measured anywhere from 120 ms to 2,700 ms — that spread was the machine sitting at load 14 under a pile of parallel work, not the query. On a loaded box, cold I/O and CPU contention dominate everything here, so treat these as a floor, not a guarantee.

What is deliberately not optimised

No FTS5 index. It would turn the 231 ms rare-term search into single-digit milliseconds, but it has to be built and kept current at snapshot time, and search is run a handful of times per session. The cost is not worth paying for a query that is already fast whenever it matters. If search became a hot path, this is the one change to make.

Test plan

Testing by layer

The system is a stack — transport, dispatch, query, SQL, files — and each layer can fail in ways the others cannot see. The plan tests each at the level where its failures actually live, rather than pushing everything through one end.

The gap this session closed

The 80 tests that existed all sat below the transport. The server, the handshake, zod validation, and dispatch were only ever checked by hand. The new protocol layer (11 tests) spawns the real binary and drives it over the wire, so the exact path Claude Code uses is now covered — including that a schema-violating limit and an unknown tool name are both rejected rather than executed. 91 tests total.

What the fixture proves

Tests run against a hand-built SQLite store, not your real data, so they are deterministic and safe in CI. It deliberately reproduces the two traps that caused real bugs: ZCONTACTNAME as the empty string on every row, and ZPUSHNAME as base64 protobuf. Two tests assert directly that no sender renders blank and no protobuf leaks — the failures those columns cause are silent, so they need naming out loud.

Not yet covered

  • The CLI adapter — cli.ts argument parsing has no test; it is exercised only by hand. Lower risk than the server, since it shares the query layer, but it is the remaining untested surface.
  • Snapshot fidelity against the live store — verified once by hand (row-count parity with the prior implementation), not in the automated suite, because it needs a real WhatsApp container to run against.
