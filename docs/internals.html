Topology

Four layers, one direction

Dependencies point strictly downward. Nothing in queries/ imports an adapter, and no adapter imports another. That is what makes the CLI and the MCP server incapable of disagreeing: they are siblings over a shared core, not variations of each other.

Layer contracts

LayerMayMust not
Leaf
schema · db · types		 Define constants, open handles, own filesystem paths, declare shapes and errors Import any query module or adapter. Know that MCP exists.
Queries
queries/*		 Take a DatabaseSync, run SQL, return plain data, throw the typed errors Open or close a handle. Read process.env. Format output for humans. Catch its own errors.
Adapters
tools · cli		 Own handle lifetime, validate input, catch typed errors, format output Contain SQL. Import each other.
Entry
server · cli		 Wire a transport, parse argv Anything else.
Why queries never open handles

Handle lifetime belongs to whoever knows when the request ends. A query function that opened its own connection could not be composed — and readChat calls resolveChat, which would mean two connections for one logical read. Adapters open once, pass down, close in a finally.

Data model

The empty-string trap, concretely

ZCONTACTNAME is '', not NULL. SQL COALESCE only skips NULL, so it returns the empty string and every sender in every group renders blank — with no error anywhere. NULLIF(x, '') around each candidate is load-bearing, and two tests assert on it by name.

Algorithm

Resolving a sender

The one genuinely intricate piece. It is a single SQL CASE with a six-rung COALESCE, evaluated per row, backed by five LEFT JOINs. Rungs are ordered most to least authoritative.

// schema.ts — SENDER_SQL CASE WHEN m.ZISFROMME = 1 THEN 'Me' ELSE COALESCE( NULLIF(cg.ZFULLNAME, ''), // 1. address book, via @lid ← group senders NULLIF(cd.ZFULLNAME, ''), // 2. address book, via phone JID ← 1:1 senders NULLIF(ppl.ZPUSHNAME, ''), // 3. self-set name, keyed by @lid NULLIF(ppd.ZPUSHNAME, ''), // 4. self-set name, keyed by phone JID NULLIF(gm.ZMEMBERJID, ''), // 5. raw @lid NULLIF(m.ZFROMJID, ''), // 6. raw JID '(unknown)' ) END // deliberately absent, and must stay absent: gm.ZCONTACTNAME // '' on all 16,802 rows → blanks every sender m.ZPUSHNAME // base64 protobuf, not a name
RungSourceReaches
0ZISFROMME = 1 → "Me"Your own messages, which carry no sender row at all
1ZMEMBERJID → ZLID → ZFULLNAMESaved contacts in group chats — the bulk of traffic
2ZFROMJID → ZWHATSAPPID → ZFULLNAMESaved contacts in 1:1 chats
3–4ZWAPROFILEPUSHNAME, either keyPeople never saved, who set their own name
5–6the raw identifierStrangers in large groups. ~37% of rows; no local name exists for them.

Measured coverage on the real store: 63% resolve to a human name. The remainder are neighbours in 19,000-message building groups who were never added to the address book — not a bug, an absence of data.

Reference

Types and signatures

Leaf: db.ts

snapshot(dest = DATA_DIR): string
Copies the three databases plus their -wal, checkpoints, chmods 0400. Never copies -shm. Throws SnapshotMissingError if WhatsApp is not installed.
openSnapshot(dataDir = DATA_DIR): DatabaseSync
Opens read-only and ATTACHes contacts and lid. Substitutes empty in-memory tables when either is absent, so the joins stay valid.
snapshotAgeSeconds(dataDir = DATA_DIR): number | null
Drives the staleness hint every tool returns.
mediaPath(relative, root = MEDIA_ROOT): string | null
null when the attachment was never downloaded. The root parameter exists so tests can substitute a synthetic tree — it is what made the media layer testable at all.

Leaf: schema.ts

tsSql(column): string
Wraps a column as datetime(col + 978307200, 'unixepoch', 'localtime').
toCoreData(value): number
Parses YYYY-MM-DD as local midnight. Throws RangeError otherwise. Paired with tsSql so filtering and display agree.
messageTypeLabel(code) · sessionKindLabel(code)
Known codes to names; unknown codes to type:N / kind:N rather than a guess.

Queries

listChats(db, { query?, kind?, limit? }): Chat[]
Aggregates counts per chat. Over-fetches ×8 when filtering by kind, since the filter applies after grouping.
resolveChat(db, term): Chat
Name, unique substring, or numeric id. Queries ZWACHATSESSION alone rather than reusing listChats. Throws ChatNotFoundError or AmbiguousChatError — the latter carries .matches.
readChat(db, chat, { limit?, since?, until?, mediaOnly? })
Queries newest-first so LIMIT keeps the most recent, then reverses to present oldest-first. until is exclusive.
searchMessages(db, term, { chat?, sender?, since?, until?, limit? }): Message[]
LIKE scan, no full-text index. Skips NULL text, so bare attachments never match.
resolvePhone(db, rawNumber): PersonMatch
Strips non-digits, then tries address book by JID, by normalised phone, by @lid; then push names; then a 1:1 chat title. bestName collapses the chain.
daySummary(db, date?): DaySummary
Splits participated from activeOnly on whether you sent anything. Day boundaries local. Defaults to today via SQL date('now','localtime').
findMedia(db, { kinds?, chat?, sender?, since?, until?, onDiskOnly?, limit?, mediaRoot? })
Returns metadata without copying. Over-fetches ×4 when onDiskOnly, since existence is checked in JS.
exportMedia(db, destinationRoot, options): MediaExport
Documents keep their original filename, sanitised to letters, digits, ._-. Other kinds get timestamp_direction_uuid. Never-downloaded items are counted in missing, not dropped.

Failure modes

Error taxonomy

Four typed errors, each thrown by the query layer and caught by adapters. The distinction that matters: two of them are recoverable by the caller and become data, not failures.

ErrorThrown whenAdapter behaviour
AmbiguousChatErrora substring matches several chatsMCP: { error, candidates[] } so the model can choose. CLI: prints the list, exit 1.
ChatNotFoundErrornothing matchesMCP: { error }. CLI: message, exit 1.
RangeErroran unparseable dateMessage naming the expected format. MCP mostly prevents this earlier via zod's YYYY-MM-DD pattern.
SnapshotMissingErrorno snapshot, or WhatsApp absentInstruction to run wa snapshot.
Ambiguity is a feature

"סן מרטין" matches 14 chats. Guessing one would be worse than failing, so the error carries all 14 names and the model picks. This is why the query layer throws rather than returning null — the failure has a payload.

Extending

Adding a tool

Four steps, in this order. The layering makes the order matter: the query exists and is tested before anything can call it.

  1. Write the function in src/queries/. Take db first, an options object second. Return plain data. Throw the typed errors; catch nothing.
  2. Add tests against the fixture in test/. If it needs data the fixture lacks, extend test/fixture.ts — and expect to update the counts other tests assert on.
  3. Register it in src/tools.ts: a zod schema, an annotation (READ_ONLY unless it writes), and a body that is json(withDb(…)) and nothing more.
  4. Add a case to src/cli.ts so it is reachable without a model in the loop.

Then extend test/server.test.ts to call it over the wire. The tool count assertion there will fail until you do, which is deliberate.
